## Finding

`RecommendationReportService.TryRenderMapAsync` currently passes `candidate.Metrics.Path` to `StaticMapMarker`. `RouteMetrics.Path` is a flattened concatenation of `PathSegments`; when Geoapify returns a disconnected `MultiLineString`, the map model receives one continuous segment. The static-map renderer therefore draws an artificial connector between the components. This is consistent with the erroneous route strokes in the supplied screenshot.

## Recommendation

Pass both the flattened compatibility path and the original `candidate.Metrics.PathSegments` into `StaticMapMarker`. Add a report-service regression test with two widely separated route components and assert that the captured static-map request keeps exactly two segments. Keep existing hosted-map serialization, which already emits each `PathSegments` member separately.

## Approved amendment — implementation and verification

### Diagnosis

The report service requests walking routes for ranked hotels whose current road distance is below 3 km. It stores those as `WalkingMetrics`, but constructs each map marker with `candidate.Metrics.Path` and `candidate.Metrics.PathSegments`. The overview draws those marker paths. `StaticMapComposition.CreateDetail` separately replaces the paths with `WalkingMetrics` for the detail panel. As a result, a nearby hotel can show its original route in the overview and its walking route in the detail panel under the same hotel color. This is the concrete source mismatch visible in the supplied report; it is not a coordinate-order or disconnected-segment issue.

### Recommended change

For hotels with a successfully requested walking route, use `WalkingMetrics.Path` and `WalkingMetrics.PathSegments` on the marker itself, so overview and detail use the same actual walking route. Preserve the current original route for hotels without a walking route. Keep marker order and the detail panel's first-two-in-ranked-order selection unchanged. Reduce destination pin scale from 1.5 to 1.1, keeping red.

### Planned proof

1. Add a failing `RecommendationReportServiceTests` case where the original route and walking route have different coordinates; assert the captured map marker uses the walking route in its primary path and segments.
2. Add/adjust composition coverage to assert detail still includes the first two eligible markers by ranked-list order, independently of walking distance.
3. Change destination pin scale to 1.1 and update its assertion; retain the red legend and pin color.
4. Render and inspect a real Geoapify-backed PDF, comparing the same hotel's overview and detail path against its walking route geometry.
5. Run `scripts/check`, obtain independent read-only review, and update acceptance evidence.

## Approved amendment — implementation evidence

### Finding

Both map implementations synthesize a venue-to-hotel straight line when `PathSegments` is empty: the hosted Geoapify provider creates a polyline fallback in `CreateRouteGeometries`, and `StaticMapOverlay.DrawRoutes` has the same fallback. These strokes are not provider road geometry and can look like incorrect routes. The screenshot also shows the nearby detail panel taking roughly 40% of the map width.

### Recommendation

Render only the full-width overview, retaining all ranked hotel markers and their available routes. Remove the straight-line fallback from hosted and schematic drawing; a marker with no route geometry should have no route stroke. Preserve returned geometry segments, the prior approved walking-route selection, marker order, route colors, and the red 1.1× arrival pin.
