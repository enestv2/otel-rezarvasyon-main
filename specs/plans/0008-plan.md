## Proposed amendment — route alignment and line weight

**Approved by the user on 2026-09-27.** The supplied map image shows route strokes visibly offset from roads. Code inspection found two plausible causes: `GeoapifyRouteDistanceProvider.ParsePath` flattened every `MultiLineString` component into one point sequence, which could add false straight connectors between disconnected components; and `HostedStaticMapProvider` rendered routes locally using a separately calculated projection over Geoapify raster tiles. The approved approach adds a failing regression test for multipart geometry preservation, then sends route geometries to Geoapify Static Maps in the same request as the raster so its renderer shares the exact projection; venue and hotel badges remain local overlays. Route casing is reduced from 7 px to 5 px, selected route from 5 px to 4 px, and other routes from 3 px to 2 px. Route colors, dash distinction, selected-route emphasis, map extent, and API fallback behavior remain.

**Files expected:** `GeoapifyRouteDistanceProvider.cs` and route model/parser; `HostedStaticMapProvider.cs` and request serialization; `StaticMapOverlay.cs`; Geoapify/provider tests and hosted map tests; this spec's AC-5/AC-6 proof map. No implementation starts until this amendment is approved. The user screenshot is the reported reproduction; the first build step will add a minimal failing multipart-geometry/alignment test before changing production code.

**Acceptance proof:** `GeoapifyProviderTests.GetRouteAsync_preserves_disconnected_multiline_components_without_joining_them` proves multipart boundaries survive; `HostedStaticMapProviderTests.RenderAsync_requests_a_png_base_map_and_adds_the_overlay` inspects POST dimensions, provider-rendered geometry entries, and reduced line widths; local hosted overlay rendering omits route strokes so it cannot shift the provider-rendered routes.
